# LedgerLine Threat Register — Milestones 1–9

Milestones 2–9 controls are implemented below; residual risks remain as listed and must be audited before production.

| # | Threat | Potential impact | Planned mitigation | Current status (Milestones 1–9) | Residual risk |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **Unauthorized account access** | Viewing or acting on another holder's account | Server-side per-account authorization on every request; ownership checks in Financial Service | Implemented: holder sees only owned/permitted accounts (`view`/`withdraw`/`transfer_out`); incoming transfers need no destination approval; admins/auditor roles enforced server-side | Medium — verify per-request lock-time checks after auth milestone |
| 2 | **Session theft and impersonation** | Attacker acts as victim, moves funds | Opaque server-side sessions, token hash at rest, `httpOnly; Secure; SameSite`, rotation, CSRF, expiry | Implemented: random 32-byte tokens, SHA-256 hash at rest, HttpOnly/Lax (+Secure in production), CSRF token hash check, expiry/revocation, active-user enforcement, rate limiting | Medium — no rotation on use; privileged postgres admin can read sessions table |
| 3 | **Duplicate requests and replay** | Double debit/credit from retries | Idempotency `(actor_id, key)` + request hash, same-txn result storage | Implemented: `idempotency_records` + advisory lock + hash, same/payload replay, 409 on mismatch, atomic claim+post+store, savepoint refusals stored | Medium — no key expiry (by design); clock skew on expiry |
| 4 | **Concurrent spending** | Overdraft / negative balances under race | `READ COMMITTED` + ordered `SELECT FOR UPDATE` + conditional updates | Implemented: deterministic `ORDER BY id FOR UPDATE`, conditional `balance>=amount` in `post_journal_atomic`, concurrent-withdrawal/opposite-transfer tested | Low — test covers 2-way races; wider stress not run |
| 5 | **SQL injection** | Data breach, ledger tampering | Parameterized `pg` queries only, no string-concatenated SQL, function allow-list | Implemented: all runtime queries parameterized; posting functions fixed `search_path=public`, no dynamic SQL | Low — retain review of dynamic-SQL prohibition |
| 6 | **Privilege escalation** | Holder gains admin powers | Least-privilege DB roles (app vs migrator vs auditor), no admin bypass, server-derived actor | Implemented: `ledgerline_executor` NOLOGIN owns `SECURITY DEFINER` functions, `app` has no balance/ledger writes, actor derived from raw session token hashed in DB (no actor param), register cannot set `role`; pool uses `DATABASE_URL` only (never `MIGRATIONS_URL`), `post_journal_atomic` re-validates actor-active/role/direction/status/session under locks; runtime `ledgerline_app` cannot READ stored `sessions.token_hash` (column-level), cannot UPDATE `users.role`/`is_active`; bootstrap offline-only via `post_bootstrap_opening` (not granted to app) | Medium — see residual trust boundary below |
| 7 | **Direct database manipulation** | Balance/ledger edits outside pipeline | `REVOKE UPDATE/DELETE` + immutability triggers + `SECURITY DEFINER` posting function | Implemented: `BEFORE UPDATE OR DELETE` `forbid_update()` on journals/postings, `REVOKE UPDATE/DELETE` from `app`, balances writable only via functions | Medium — superuser/migrator can bypass triggers |
| 8 | **Duplicate external deposits** | Phantom money from double-claimed funding | Unique `external_reference` + maker-checker verification (initiator≠verifier, holder≠verifier) | Implemented: unique `external_reference` on `deposit_requests` + journal, maker≠checker and checker≠holder checks, `409` on duplicate | Medium — no external bank webhook in v1; manual evidence accepted |
| 9 | **Insider abuse** | Admin creates funds, reverses audit | Separation of duties, audited admin actions, no admin balance bypass, seed restricted to system | Implemented: dual-admin adjustments, maker-checker deposits, audit_events for admin/security actions, no HTTP seeding; bootstrap only via `db/bootstrap.sql` offline | Medium — single admin collusion not prevented |
| 10 | **Ledger corruption** | Unbalanced journals, projection drift | Deferred balanced-journal trigger (sum=envelope=type rules) + reconciliation job | Implemented: exactly-2 equal postings by construction + DB-layer direction/status/role/session checks, partial reversal uniqueness (`reversal_of` count check + row lock), `GET /audit/reconciliation` recomputes from ledger, alerts on discrepancy, no silent correction; `?hw=`-bound statement traversal; committed refusal records | Low-medium — trigger sum check is by-construction + recomputation, not a separate `CHECK` |
| 11 | **Denial of service** | Lock contention, huge payloads, log flooding | 16 KB JSON limit, Helmet, lock/statement timeouts, rate limiting, pool caps | Implemented: 16 KB limit + Helmet; shutdown idempotent with 10s force-close and EADDRINUSE handling; graceful shutdown sets exit code 0 and exits naturally (no `process.exit(0)`), forced timeout calls `closeAllConnections()` and exits non-zero | Medium |
| 12 | **Sensitive information leaking through logs** | Tokens/passwords in logs | Pino redaction (cookies, auth headers, tokens), allowlisted error metadata only, query/body stripped, `headersSent` delegation, generic 500s, no stack/query in logs | Implemented: redaction + no raw `url`/`originalUrl`/`path`/`baseUrl` logging (safe route template only via `safeRouteTemplate` returning `req.route.path` verbatim, e.g. `/accounts/:accountId`; `baseUrl` and all request-derived segments are ignored so parameterized mounts cannot leak; unmatched paths omitted) + generic 500s; malformed JSON 400 only for `entity.parse.failed`, internal `SyntaxError` → 500; env config via `node --env-file-if-exists=.env` with process-env precedence and missing-file tolerance | Low for foundation; must audit after auth/session added |

Implementation status legend: **Implemented** = present in this milestone; **Partial** = foundation control only; **Not implemented** = planned for future authorized milestone.

## Residual trust boundary
A compromised application process (with `ledgerline_app` credentials) can mutate non-ledger tables but cannot post journals or change balances except through `SECURITY DEFINER` functions; a PostgreSQL superuser/migrator with credential access can still tamper with ledger rows (e.g., `SET session_replication_role`/`ALTER TABLE DISABLE TRIGGER`, direct `UPDATE`). This is inherent to shared-database deployments and is not mitigated in v1; it requires separate DB-credential isolation, audit-log immutability, and operational monitoring before production.
